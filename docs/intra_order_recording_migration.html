Architecture migration note

Intra 订单记录与因子存储迁移设计

订单事件、盘口回补、tlen 执行和定频因子分别建模；在线交易热路径与 ClickHouse 研究数据链路异步隔离。

Executive summary

设计结论

当前问题的根源不是 RocksDB 写得慢，也不是 persist manager 少订阅了一个频道，而是把两种完全不同的数据模型放进了同一条订单记录。

订单是一张稀疏的执行事件表；因子是一张连续的时间序列特征表。不能依赖订单状态变化来记录连续因子。
保持不变
BBO 回补逻辑
继续按订单 update_ts，在两腿盘口环形缓存中分别取不晚于该时间的最后一条 BBO。
在线迁移
tlen 移到 pre-trade
pre-trade 直接维护价位可见量，负责开仓 gate、活动订单监控和撤单，不再和 trade_signal 往返推送候选。
研究数据
定频因子进入 ClickHouse
baseline、fusion、model、vol 由独立 recorder 聚合成具名列；盘后按无未来原则对齐订单。
最终分工 内存负责实时判断；RocksDB 保存订单、成交、延迟、BBO 和 tlen 等稀疏数据；ClickHouse 保存 baseline、fusion、model、vol 和 tradeflow 等定频数据。
01 / Data model

数据模型边界

订单事件按状态变化记录；因子按固定时间桶记录。两者使用独立的采样频率、时间语义与存储结构。

数据类型一行代表什么自然主时间合适的存储
订单事件一次 New、Fill、Cancel 等状态事实订单 update_tsRocksDB
BBO 回补订单事件发生时，两腿最后已知盘口交易所盘口时间订单记录附加字段
tlen报单、撤单或关键订单事件处的价位可见量快照决策使用的订单簿时间pre-trade 内存状态 + 订单事件稀疏字段
定频因子某 symbol 在某个时间桶的特征向量bucket_ts + available_tsClickHouse 具名列

04 / BBO sampling

BBO 触发采样与左向回补

订单记录保存构成价差的两腿 BBO，不固化单一价差值；ask-bid、bid-ask 和 mid spread 均由原始 BBO 重算。

触发采样

from_key 保存 trade_signal 决策时的 open_bid/open_ask/hedge_bid/hedge_ask。

用途：定位交易信号使用的市场输入。

回溯采样

persist manager 根据订单 update_ts，回看两腿 BBO ring。

含义：订单状态变化发生时，交易所时间轴上的市场状态。

回补执行步骤

persist manager 独立订阅两腿 BBO
按 venue + normalized symbol 分别维护环形缓存。
收到 uniform order 后暂存
默认等待 500ms，让可能稍晚到达的 BBO 有机会先进入 ring。
分别执行 find_le(update_ts)
open 与 hedge 各取一个 exchange timestamp 不大于 update_ts 的最新样本。
追加十个 BBO 字段
两腿各保存 tp、bid、bid_qty、ask、ask_qty，然后写入 RocksDB。
current Rust: retrospective lookup 
let open = rings
    .get(&(open_venue, symbol.clone()))
    .and_then(|ring| ring.find_le(order.update_ts));

let hedge = rings
    .get(&(hedge_venue, symbol))
    .and_then(|ring| ring.find_le(order.update_ts));

// find_le returns the last sample satisfying:
// sample.exchange_ts <= order.update_ts
迁移约束：回补算法保持不变 扩展字段包括 open_bbo_age_us、hedge_bbo_age_us 和两腿 found 标记，用于标识样本陈旧度和缺腿状态，不改变样本选择结果。
回补边界 ring 按条数限制容量，乱序样本直接丢弃，且没有最大陈旧度检查；命中历史样本不代表该样本满足新鲜度要求。
05 / tlen execution

tlen 获取与执行迁移至 pre-trade

pre-trade 在持有候选订单和活动订单状态的同一进程内读取 tlen，并直接完成开仓 gate、活动订单监控和撤单执行。

当前 tlen 采用请求-响应模型，记录覆盖完全跟随查询时点。每增加一个取值时点都要重新发起请求；迁移只改变获取位置和执行归属，稀疏记录方式保持不变。
记录时点迁移前迁移后
每次报单请求 tlen，并写入报单 from_key从 pre-trade 本地状态读取并记录
订单存续期盘口变化没有查询，不新增记录只更新 pre-trade 内存，不新增记录
普通撤单保留报单时 tlen，没有撤单时点值撤单处理时直接读取本地当前值
tlen 触发撤单触发查询，因此能够记录触发时点值直接使用本地阈值状态并稀疏记录

迁移前：通过消息链路获取 tlen

迁移后：pre-trade 本地读取 tlen

记录方式保持不变 tlen 只在开仓判断、阈值穿越、撤单动作和订单状态事件处记录；pre-trade 内存中的中间变化不形成定频序列。
异步 tlen event 是可选扩展 基线迁移不产生独立 async tlen event，只在既有稀疏订单记录中附加当前值。研究或监控需要更细的阈值穿越与状态变化时，可增加异步事件流；该事件流与交易执行解耦。
06 / Feature recording

定频因子独立记录到 ClickHouse

baseline、fusion、model 和 vol 已经通过 IPC 持续产生数据。当前 trade_signal 只保存每个 symbol 的最新值，并在交易信号出现时抽取其中少数字段写入 from_key。

内存聚合按 watermark 封桶

字段含义记录目的
bucket_ts这组值描述哪个市场时间桶研究横截面和 bar 对齐
source_event_ts每个来源自己声明的观测时间识别不同来源是否真的属于同一桶
source_available_ts该值最早什么时候可供策略使用防止回测未来数据
ingest_tsrecorder 实际接收时间监控 IPC 延迟、迟到和积压
schema_version因子 ID 到列名的版本factor plan 变更后仍能解释历史值
source_mask / ready哪些来源到齐、哪些值已 warm up区分缺失、未就绪和数值 0
时间单位契约必须先统一 trade flow 生成 bar.start_ms，fusion 当前又按微秒处理 msg.ts；迁移前必须用真实 IPC 样本确认并固化单位，否则 factor/model 时间存在 1000 倍偏差。
fusion 增加 schema ID 当前 FeatureMsg 只有 feature_dim 和位置向量，没有 factor ID。缺少 schema_id 或严格版本化的 factor registry 时，位置向量无法稳定映射为具名列。
07 / Analytical storage

ClickHouse 承担因子列存与盘后对齐

ClickHouse 长期表只保存定频数据：一行对应一个时间切片，一列对应一个具名变量。

研究任务from_key / RocksDBClickHouse

单个订单的低延迟点查RocksDB 更合适不是 ClickHouse 的主要目标

宽表结构

ClickHouse DDL 
CREATE TABLE research.factor_snapshot_5s
(
    bucket_ts             DateTime64(3, 'UTC') CODEC(Delta, ZSTD),
    snapshot_available_ts DateTime64(6, 'UTC') CODEC(Delta, ZSTD),
    venue                 LowCardinality(String),
    symbol                LowCardinality(String),
    schema_version        UInt32,
    ingest_version        UInt64,

    tradeflow_close       Float64,
    fusion_baseline_118   Float64,
    model_score           Float64,
    model_quantile        Float64,
    vol                   Float64,

    tradeflow_ready       UInt8,
    fusion_ready          UInt8,
    model_ready           UInt8,
    vol_ready             UInt8,
    source_mask           UInt8
)
ENGINE = ReplacingMergeTree(ingest_version)
PARTITION BY toYYYYMM(bucket_ts)
ORDER BY (venue, symbol, bucket_ts, schema_version);

数值列与 ready 列成对保存。这样 0 可以继续表示真实数值 0， ready=0 表示缺失或未 warm up，避免依赖 Nullable 带来的额外语义和开销。

add one factor

盘后无未来对齐

订单窗口盘后从 RocksDB 导出为临时输入，再与 ClickHouse 定频因子表做 left as-of 对齐；订单事实仍以 RocksDB 为长期存储。

execution-time ASOF JOIN 
SELECT
    o.client_order_id,
    o.symbol,
    o.signal_ts,
    f.bucket_ts,
    f.model_score,
    f.vol
FROM research.order_event_input AS o
ASOF LEFT JOIN research.factor_snapshot_5s AS f
    ON  o.venue = f.venue
    AND o.symbol = f.symbol
    AND f.snapshot_available_ts <= o.signal_ts
WHERE o.trade_date = '2026-08-04';
执行复现使用 available_ts bucket_ts 表示“数据描述哪个市场时间”；available_ts 表示“策略什么时候真的能看到它”。执行复现必须满足 available_ts 不晚于 signal_ts，否则会把事后才计算出的模型结果带回过去。

可复用的现有能力

宽表和自动加列

db_fusion_factor_replay 已创建 ReplacingMergeTree 宽表，并为配置中的具名因子执行 ADD COLUMN。

批量 RowBinary writer

tardis_ipc_replay 已有有界队列、独立写线程、batch_rows 和 flush interval，可以抽成公共库。

现有表形态复用 live recorder 与现有 replay 表共用列命名和 RowBinary 编码，跨 venue 查询由 UNION VIEW 提供，避免形成两套不兼容的 schema。

ClickHouse 列存只读取查询涉及的列，MergeTree 使用排序键和分区减少扫描，ASOF JOIN 支持“不晚于事件时间的最近记录”。 详细依据可见 列存原理、 MergeTree、 ASOF JOIN 和 批量写入策略。

08 / Change sizing

大、中、小修改量评估

这里的大小同时考虑代码量、跨进程范围和真实交易风险。修改文件少但会改变撤单行为，仍然属于“大”。

小
单模块、无行为迁移
约 1 至 3 个工程日。主要是字段、监控、局部测试或复用现有组件。
中
跨进程或新增契约
约 1 至 2 个工程周。需要 IPC、schema、集成测试和故障恢复。
大
真实交易语义变化
3 个工程周以上，并需要 shadow、灰度、回滚开关和生产观察期。
修改项量级影响面主要工作与风险
保留 BBO 回补，新增 age/found小persist_manager字段扩展、二分回看测试、缺腿和陈旧度指标
统一 timestamp / factor schema 契约中baseline、fusion、model、vol修复单位歧义，增加 schema/model version 和兼容解析
feature_recorder + 多 IPC 订阅中新进程订阅管理、序列缺口、source normalization
内存桶聚合 + ClickHouse 宽表中新进程 + ClickHouse可复用已有 RowBinary writer 和自动加列逻辑
本地 outbox、重试和幂等中feature_recorder仅作为 ClickHouse 写入失败时的临时重试缓冲
pre-trade 维护 TlenBook shadow中pre_trade + depth IPC复用/抽取 local_tlen，比较新旧 exact tick 结果
开仓 gate 与撤单执行权切换大trade_signal + pre_trade直接改变订单接受/拒绝/撤单行为，涉及重启恢复和 orphan
既有订单事件附加当前 tlen小pre_trade + persistence复用报单、撤单等稀疏记录时点，不新增定频 tlen 数据流
可选 async tlen event中pre_trade + persistence仅在研究或监控需要细粒度变化时启用，与交易热路径异步隔离
订单临时输入与盘后 ASOF 对齐中RocksDB export + ClickHouse订单只按查询窗口临时导入，长期存储仍在 RocksDB
缩减 from_key中trade_signal + 研究脚本旧数据兼容；最终只保留 decision/schema/snapshot ID 和 reason
总体评估：大 ClickHouse 接入本身因为已有代码可复用，属于中等修改。总体之所以是大，主要来自 tlen 在线执行权迁移及其生产恢复语义。
09 / Final storage

最终存储形态

RocksDB 保存订单及其延迟、BBO、tlen 等稀疏事件；ClickHouse 保存按固定时间桶产生的因子、模型、波动率和 tradeflow 数据。

长期存储数据形态保存内容写入方式
RocksDB稀疏事件订单与成交、生命周期时间戳和延迟、订单时点 BBO 回补、报单与撤单时点 tlen由 New、Fill、Cancel、Trade 等事件触发
ClickHouse定频列存baseline、fusion factor、model、vol、tradeflow feature 及其时间和 ready 状态按 5s/60s 时间桶聚合后批量写入
