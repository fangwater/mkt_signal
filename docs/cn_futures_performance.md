# 国内期货交易热路径性能

CTP 与易达共用单业务线程的风控、OMS 和后台持久化。默认报单与回报都异步落盘，发送不等待 fsync；同步发送选项、完整恢复屏障及正常关闭仍等待实际持久化。本轮测试均离线，没有生产部署。

## 已实现的五项优化

1. 原始委托／成交回报只解析一次，恢复状态机、OMS 和落盘投影复用同一解析结果。OMS 借用更新参数，先验证数量、身份、冻结仓位，再原地更新订单，避免克隆整笔订单；原始证据仍先可靠入队。
2. 易达待确认报撤使用可立即删除节点的最小堆，最近到期时间 O(1) 读取、登记／完成 O(log n)。空队列不采时钟，没有历史扫描或惰性过期节点；超时仍停止交易并保留冻结，不自动重试。
3. 去掉易达历史引用表和累计 20 万条限制。非零组回报直接使用交易所、交易日、报单组、引用；组 0 撤单按系统号区分。CTP 保留紧凑的数值请求关联与按引用索引，支持迟到错误回报；跨会话引用歧义仍拒绝猜测。CTP 完整恢复中的累计订单／成交数量上限也已移除。
4. 后台每次收取当前已经可用的最多 64 条记录，以一个同步 WAL WriteBatch 提交，不等待凑批。批内投影能看到前缀；冲突只保留合法前缀及错误证据，后续记录失败。确认、ready 和发送回执在成功提交后发出。详见[持久化保证](cn_order_persistence.md)。
5. 合约、仓位、订单及未结索引改用内部数值槽位；未结集合按合约维护，swap-remove 删除，并缓存待开仓手数。订单默认预留 4096 个槽位，`preallocated_orders` 可提高容量，恢复后保留该提示，历史可继续增长。原始回报和发送前审计直接复制到预分配队列槽位，后台构造 JSON。

外部 OrderKey、原生成交身份和 RocksDB 记录保持统一契约，内部槽位不持久化。未结仍以 `remaining() > 0` 为准：终态先到、事实成交未到时继续冻结风险额度。完整状态查询和重连恢复仍处理账户历史；订单字符串、归一化投影和成交去重仍会分配内存，整条交易路径并非零分配。

## 本地微基准

2026-11-11，AMD EPYC 7642 共享主机，业务线程固定 CPU 190，后台线程继承原 CPU 集合，CPU 未隔离。基线为上一轮提交 `6c514f6c`；前后均为默认 feature 的 release 构建，三轮交错运行，每轮 15 批 × 128 次。计时含线程内分配计数开销，未加载 SDK、未连接网络。表中为三轮分位数的中位数，原始记录见 [JSON](benchmarks/cn_futures_native_optimization.json)。

## 完整本地 SDK 链路

新增 `native_pipeline` 基准使用正式易达头文件、真实 Rust 适配器和 C++ 桥接，动态库为带专用标记的合成 SDK；程序在启动前拒绝不带标记的库。配置仅含 fixture 凭据和 loopback 占位地址，不读取私有账户文件，不加载厂商传输实现。TCP／UDP／XTCP 名称只覆盖适配器配置分支，下面的差异不能解释为三种真实网络传输的性能差异。

生产循环与基准共用 decode、OMS 更新和持久化投影入口。`latency-metrics` 仅在基准构建启用，增加单调时钟采样；默认生产构建没有该采样。`callback→OMS` 从 Rust 收到原生回调起算，含回调队列等待、原始证据入队和 OMS 更新，到完成 OMS 为止；不包含后续归一化落盘等待。每组 2,000 轮、4,000 次原生请求：FAK 开／平或被动报／撤。

| 配置／场景 | 原生报单桥接调用 p50 / p99 / p99.9 | 回调→OMS p50 / p99 / p99.9 | 持久化记录 / WAL 批次 | 观察到的队列积压峰值 |
| --- | ---: | ---: | ---: | ---: |
| TCP，FAK 开平 | 2.785 / 100.198 / 246.314 µs | 12.273 / 102.102 / 537.952 µs | 40,085 / 720 | 640 |
| UDP，FAK 开平 | 3.617 / 15.981 / 434.398 µs | 16.441 / 46.828 / 1,270.822 µs | 40,038 / 659 | 2,496 |
| XTCP，被动报撤 | 2.995 / 52.058 / 95.580 µs | 6.603 / 105.609 / 156.274 µs | 18,086 / 387 | 288 |

三组最大 WAL 批次均为 64。按完整测试墙钟计算，分别约 19,970／17,772／21,287 条证据每秒；包含业务处理、JSONL 与显式持久化屏障，不是磁盘极限吞吐。积压是生产者采样观察值。每 32 或 128 轮等待一次屏障，突发处理至持久化的 p50 分别为 31.88／144.90／13.30 ms；每组只有 62 或 15 个突发样本，不足以估计稳定的 p99.9。完整原始分位数、提交路径和终态路径保存在 JSON。

每组退出后实际重开 RocksDB 并导出核对：FAK 两组各新增 4,000 个订单和 4,000 条成交事实，被动撤单组新增 2,000 个订单、没有新增成交；各组还保留 2 条恢复订单。完成后的待确认请求为 0，仓位回到测试前值。

另在关闭持久化的条件下连续运行 220,000 次 FAK 请求，覆盖旧 20 万条边界。待确认请求归零，最早订单迟到回报仍可关联，重复成交未重复计仓。该组回调→OMS p50 / p99 / p99.9 为 3.938 / 9.297 / 16.722 µs，约 102,837 次本地请求每秒。该数字不能用作启用落盘后的吞吐，也不含真实网络或柜台 RTT。

CPU 编号应改为本机允许使用的核，输出目录必须尚不存在。微基准使用独立临时 RocksDB，并正常关闭和删除；完整链路脚本保留离线日志和导出以便核对。两者均不发送真实订单。

本轮双 SDK 核心、共享契约和持久化单测分别为 110／17／78 项通过。覆盖 25 万次 deadline 完成即删除、21 万次 CTP 请求后迟到关联、身份作用域、规则重排与遗漏、原地更新失败不污染状态、终态先到冻结、批内事实去重／冲突、WAL 失败不推进状态、同批恢复屏障，以及多个异步意图在确认屏障后直接退出进程的恢复。易达 42 个逐场景重开 DB 的桥接场景、已有仓位保护场景及 CTP 桥接通过。Clippy `--no-deps -D warnings`、格式检查和 release 构建通过。
