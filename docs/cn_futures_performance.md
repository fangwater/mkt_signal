# 国内期货交易热路径性能

## 订单热冷分离与易达统一 placement

共享 OMS 的订单由一个完整 `OrderSlot` 改为同一 OrderId 索引的两组连续存储：热槽位保存状态、手数、资金/持仓冻结、方向、价格类型、数值合约和未结索引；冷槽位保存原始 Intent、完整 OrderKey 和系统号。所有可变数值状态只在热槽位维护。恢复、扩容及订单替换同时维护两组存储；外部身份和 RocksDB/JSON 契约不变。

当前 Linux x86-64 编译结果：原槽位 192 字节，热槽位 72 字节、冷身份 120 字节。热扫描步长减少 62.5%，两组固定字段合计仍为 192 字节；这不是整条下单延迟下降 62.5% 的测量。自成交检查、未结数量维护、本地拒绝及撤单释放直接访问热槽位。`TradingCore::order()` 返回无分配的只读 `OrderView`，序列化与原 `Order` 完全一致；冷消费者可调用 `to_order()` 构造拥有完整身份的订单。审计仍复制定长状态入队，后台生成统一记录。报单准备中的字符串分配尚未消除。

易达与 CTP 复用同一个 placement 实现。易达 `[placement]` 可配置同 NUMA 节点上的业务核、SDK 核集合和后台核集合，跨域不共享 SMT 物理核；配置后严格 `MPOL_BIND`，权限或拓扑错误直接失败。SDK 创建、启动、登录、重连、销毁使用 SDK 域，输入与数据库/审计后台继承后台域，业务核心和队列在绑定之后分配。同步报单回调保留业务域，SDK 工作线程回调强制 SDK 域。原 `business_core` 配置已移除，迁移方法见 [易达文档](yida_trade.md)。省略 placement 时仍按 OS 默认调度，不保证核隔离或 NUMA 归属。CTP 的每域单核及组合行情布局要求继续由其配置校验强制执行。

本轮只运行 Yida/共享核心的明确筛选测试和易达合成 SDK 链路；CTP 与混合测试只编译，不执行。原生 OS 测试覆盖多核 SDK/后台集合、同步/异步回调亲和性、内存策略及退出恢复。新增核心覆盖热冷完整投影、终态先于成交、迟到成交与撤单释放、拒绝错误更新、扩容/恢复、未结 swap-remove 以及非规范完整引用。46 项明确筛选的安全单测通过；易达合成 SDK 47 个场景通过，其中 45 个实际重开 RocksDB 核对，最后的 affinity 场景验证业务/后台亲和性、NUMA 本地页和同步报撤。默认 feature 的全目标检查、双 SDK 全目标 Clippy、格式检查与易达 release 构建通过；双 SDK 检查只编译，不运行 CTP。真实柜台 RTT 未测量。

## 回报投影、报单分配和尾延迟优化（基线 5460fdfd）

本轮以 SDK `1.502.55.35` 的提交 `5460fdfd` 为基线。共享开发目录同时有未提交的 CTP 接入修改，因此在该提交的独立 worktree 验证本轮代码，提交范围包含以下三项，保留其他任务的工作区修改。

- 实时订单／成交投影改为复制定长状态快照入队，后台再构造统一 `NativeOrderRecord` / `NativeTradeRecord`。合约元数据在核心中不可变共享，快照持有对应的 `Arc`，规则刷新、订单继续成交或恢复都不会改变已入队记录。成交和它的订单投影仍在同一个事件、同一个 WriteBatch 提交；多订单投影仍合并为一个事件。后台消费已拥有的订单值，避免再次克隆整笔订单。
- 原生数字引用直接以 `u64` 索引，并借用已有会话键，省去逐笔为索引复制引用和会话字符串。`1`、`01`、非数字及超 `u64` 的外部引用保持各自完整身份。单个意图最多产生两笔子单，规划、预备请求及回执使用内联数组；JSON 回执仍为原来的 `children` 数组。超过内联容量的原生批次照常增长。
- 启动／恢复阶段预触订单槽位的未使用存储和引用索引桶，并预留、预热限频窗口；不创建实际订单、不消耗真实引用、不填入虚假的限频历史。已有订单、限频状态和冻结仓位不受额外容量预留影响。预触页增加初始化工作和已预留容量的物理内存占用，超过容量后仍可自动增长。

## 此前实现的五项优化

1. 原始委托／成交回报只解析一次，恢复状态机、OMS 和落盘投影复用同一解析结果。OMS 借用更新参数，先验证数量、身份、冻结仓位，再原地更新订单，避免克隆整笔订单；原始证据仍先可靠入队。
2. 易达待确认报撤使用可立即删除节点的最小堆，最近到期时间 O(1) 读取、登记／完成 O(log n)。空队列不采时钟，没有历史扫描或惰性过期节点；超时仍停止交易并保留冻结，不自动重试。
3. 去掉易达历史引用表和累计 20 万条限制。非零组回报直接使用交易所、交易日、报单组、引用；组 0 撤单按系统号区分。CTP 保留紧凑的数值请求关联与按引用索引，支持迟到错误回报；跨会话引用歧义仍拒绝猜测。CTP 完整恢复中的累计订单／成交数量上限也已移除。
4. 后台每次收取当前已经可用的最多 64 条记录，以一个同步 WAL WriteBatch 提交，不等待凑批。批内投影能看到前缀；冲突只保留合法前缀及错误证据，后续记录失败。确认、ready 和发送回执在成功提交后发出。详见[持久化保证](cn_order_persistence.md)。
5. 合约、仓位、订单及未结索引改用内部数值槽位；未结集合按合约维护，swap-remove 删除，并缓存待开仓手数。订单默认预留 4096 个槽位，`preallocated_orders` 可提高容量，恢复后保留该提示，历史可继续增长。原始回报和发送前审计直接复制到预分配队列槽位，后台构造 JSON。

外部 OrderKey、原生成交身份和 RocksDB 记录保持统一契约，内部槽位不持久化。未结仍以 `remaining() > 0` 为准：终态先到、事实成交未到时继续冻结风险额度。完整状态查询和重连恢复仍处理账户历史；订单字符串、归一化投影和成交去重仍会分配内存，整条交易路径并非零分配。

## 完整本地 SDK 链路

新增 `native_pipeline` 基准使用正式易达头文件、真实 Rust 适配器和 C++ 桥接，动态库为带专用标记的合成 SDK；程序在启动前拒绝不带标记的库。配置仅含 fixture 凭据和 loopback 占位地址，不读取私有账户文件，不加载厂商传输实现。TCP／UDP／XTCP 名称只覆盖适配器配置分支，下面的差异不能解释为三种真实网络传输的性能差异。

生产循环与基准共用 decode、OMS 更新和持久化投影入口。`latency-metrics` 仅在基准构建启用，增加单调时钟采样；默认生产构建没有该采样。`callback→OMS` 从 Rust 收到原生回调起算，含回调队列等待、原始证据入队和 OMS 更新，到完成 OMS 为止；不包含后续归一化落盘等待。每组 2,000 轮、4,000 次原生请求：FAK 开／平或被动报／撤。
